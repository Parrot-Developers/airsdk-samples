# Object Detector mission

Real-time object detection with `ssd300_vgg16` (torchvision, COCO-pretrained,
used as-is, no training): the mission reads back two output tensors from
`infer()` (box regressions and class logits), decodes them itself (anchor
decoding + softmax + per-class NMS in `processing.cpp`), and publishes
detections as video-stream user metadata for `object_detector_viewer` to
overlay.

## What it does

Every camera frame, the mission resizes it to 300x300, feeds it to `infer()`
as one raw RGB input (`preProcessFrame()` does no normalization, that is
baked into the network itself), and gets back two tensors: `bbox_regression`
(one 4-value box delta per anchor) and `cls_logits` (one 91-value class score
per anchor, COCO's 90 classes plus background). `ssd_postprocess()` decodes
boxes against a fixed set of 8732 priors (`generate_ssd_priors()`) and runs
NMS per class.

## Building the model

No training, no dataset collection: the weights are the stock COCO-pretrained
ones. The only inputs needed are a handful of representative photos for
SNPE's quantization calibration.

```bash
# 1. Isolated venv.
cd object_detector
python3 -m venv .venv && source .venv/bin/activate
pip install torch torchvision onnx pillow numpy

# 2. A handful of representative photos (everyday objects/people/vehicles)
#    for quantization calibration, not a training/validation dataset.
mkdir -p calib_images
# copy 10-20 real JPG/PNG photos into calib_images/

# 3. Export (no training step: loads SSD300_VGG16_Weights.COCO_V1 as-is).
python3 tools/export.py --calib-images-dir ./calib_images --out ./out

# 4. Confirm the anchor geometry the network was exported with matches
#    generate_ssd_priors() in processing.cpp: if it doesn't, decoded boxes
#    will be positioned/sized wrong even though inference runs fine.
cat out/anchor_config.json

# 5. Convert and quantize with SNPE 2.12.0.230626.
snpe-onnx-to-dlc --input_network out/object_detector.onnx \
    --output_path out/object_detector.dlc
snpe-dlc-quantize --input_dlc out/object_detector.dlc \
    --input_list out/input_list.txt \
    --output_dlc out/ssd_quantized.dlc

# 6. Confirm the two output layer names: settings.outputLayers in
#    processing.cpp assumes "/Unsqueeze" and "/Unsqueeze_1" (SNPE *layer*
#    names, the "Name" column below, not the "bbox_regression"/"cls_logits"
#    tensor names); update processing.cpp if the real names differ. Also
#    check the "input" row: it must be "1,300,300,3", not "1,300,3,300",
#    see "Troubleshooting" below.
snpe-dlc-info -i out/ssd_quantized.dlc

# 7. Ship it
cp out/ssd_quantized.dlc assets/etc/services/detection/
```

Then build and install the mission as usual, see the [AirSDK
documentation](https://developer.parrot.com/docs/airsdk/general/sample_hello.html#build-the-hello-drone-flight-mission).

## Configuration files

* `mission.yaml`: mission descriptor; `object_detector` (C++) depends on
  `libairsdk`, `libvideo-ipc`/`libvideo-ipc-cpp`/`libvideo-ipc-client-config`,
  `opencv4` and `msghub::object_detector`.
* `assets/etc/services/detection/ssd_quantized.dlc`: shipped pre-built (the
  stock COCO-pretrained weights, no training); "Building the model" above is
  only needed to reproduce or swap it.
* `assets/etc/services/detection/classes_names.csv`: the 91 COCO category
  names (including background), fixed, not regenerated by `tools/export.py`.

## Troubleshooting

* `bad image shape. expected: (300x3x300), actual: (300x300x3)` in
  `nn_inferencesnpe`'s log at inference time, even though the network loads
  fine (`network ready`): the ONNX graph's input was declared NHWC
  (`(1, 300, 300, 3)`) with a manual permute to NCHW inside the wrapper.
  `snpe-onnx-to-dlc` always assumes an ONNX image input is NCHW and inserts
  its own transpose to its native layout on top of that assumption: given an
  already-NHWC input, the two transposes compound into a wrong axis order
  that only shows up on real hardware (`snpe-dlc-info` output alone won't
  necessarily catch it, since this model's every spatial dimension is
  square, hiding the swap in the shape table). Fixed by declaring the ONNX
  input as plain NCHW (`(1, 3, 300, 300)`, see `ExportableSSD.forward()` in
  `tools/export.py`) and letting the converter do the NHWC conversion
  itself, no manual permute.
* Quantization taking many minutes to hours: check the size of
  `calib_images/` first. A few hundred/thousand images doesn't improve
  quantization quality over ~15-20 representative photos, it just multiplies
  `snpe-dlc-quantize`'s runtime (each image is one full forward pass).

## Notes and caveats

* The two output tensors are kept separate (not packed into one), matching
  `ssd300_vgg16`'s own natural output: `onInferResult()` looks each one up
  by name (`bbox_regression`, `cls_logits`), not by position.
* `generate_ssd_priors()`'s scales, steps and aspect ratios must match
  `ssd.anchor_generator`'s exactly (see `tools/export.py`'s
  `dump_anchor_config()`); re-check this after any change to the exported
  model.
* Validated on real hardware and over the HIL bridge (mission + `airsdkd`
  on PC, `airsdkd-hil` on the drone): both give the same detections.
  Observed throughput is roughly 8-9 fps (measured from the "detected N
  object(s)" log line, which is only emitted when at least one detection
  passes the confidence threshold, frames with zero detections aren't
  logged, so this is a lower bound, not an exact figure). This figure is
  measured on an otherwise-idle device: on the actual drone the detector
  shares the SoC with the rest of the flight-critical software, and process
  times can run up to 30% higher under that contention -- budget for the
  drone, not for an idle benchmark.
